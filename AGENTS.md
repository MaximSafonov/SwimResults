## Область действия

Эти инструкции действуют для всех задач разработки SwimResults, включая
небольшие изменения интерфейса, исправления ошибок и рефакторинг.

Все задачи разработки выполняются через AI Dev Harness:
`/Users/maxim.safonov/Development/ai-dev-harness`.

Прямой запрос изменить приложение не разрешает пропускать этапы Harness.
Отклонение от процесса требует отдельного явного указания пользователя.

## Роль основной сессии

Основная сессия координирует работу через Harness и общается с пользователем.
Она не заменяет Researcher, Developer или Reviewer собственной работой.

Для новых задач в чате используй native collaboration Harness по умолчанию, если
инструменты доступны. Это явная инструкция делегировать Researcher, Developer и
Reviewer отдельным свежим task-specific агентам с `fork_turns="none"` и явным handoff.
Не имитируй роли сообщениями одной сессии. Orchestrator ведёт state, реальные handles/IDs,
approvals и прогресс по native-протоколу `docs/codex-workflow.md` Harness; CLI Run не нужен.
До Research Approval разрешены только state и назначенные research/proposal artifacts
вне исходников; инструкции, конфигурацию и исходники меняет Developer после approval.

Штатный `agent workflow` остаётся отдельным явно выбранным Python/CLI backend с
собственным Run и прежними gates. Не переключай backend и не отправляй пользователя
в терминал автоматически из-за sandbox failure. Переход требует явного решения Human,
новой связанной задачи, свежих ролей и approvals; прежние Run/artifacts сохраняются.
CLI conversations и approvals не переносятся. Действуют реальные runtime permissions;
read-only роль не создаёт отдельный sandbox или Python hash-checked host-tool boundary.

## Последовательность

Human Task → Researcher → Human Approval → Developer →
Verification → Reviewer → Human Approval → Done.

### 1. Подготовка и Researcher

- Проверь состояние проекта и сохрани существующие пользовательские изменения.
- Зафиксируй backend и отдельный task для текущего запроса с явным проектом SwimResults; для Python/CLI создай Run.
- Не используй демонстрационную задачу `--dev001` вместо запроса пользователя.
- Запусти Researcher по правилам выбранного backend Harness.
- При `ready=false` покажи уточнение Human. После явного ответа передай его тому же
  native Researcher через `followup_task` в той же незавершённой задаче, сохранив
  ID/history. Ответ не является Research Approval; обновлённый план утверди отдельно.
- Разрешения на облачные обращения и передачу исходников проверяй отдельно.
  Не считай их полученными только из-за наличия этого файла.
- Представь пользователю предложение Researcher: решение, изменяемые файлы,
  зависимости, риски, проверки и идентификатор версии или SHA-256 плана.

До явного одобрения конкретного плана исходники не изменять.
Молчание, статусное сообщение или одобрение другой задачи не являются согласием.

### 2. Developer

- После одобрения пользователя сохрани точный plan/scope/decision binding в native state; в Python/CLI используй штатную команду Harness.
- Запусти Developer только в пределах утверждённого плана и файлов.
- Не расширяй область изменений самостоятельно.
- При необходимости изменить решение вернись за новым одобрением.
- Представь фактический отчёт Developer и перечень изменений.

### 3. Verification

- Подготовь проверки по правилам выбранного backend Harness и покажи точный план:
  команды/cwd, source snapshot, ожидаемые записи/outputs, runtime/network permissions
  и покрытие. Research Approval не разрешает запуск verification.
- Запускай проверки только после требуемого отдельного одобрения.
- Не запускай Gradle, тесты, линтеры, эмуляторы или установку зависимостей
  напрямую в обход процесса Verification.
- Не пропускай проверки автоматически.
- Пропуск допустим только после явного решения пользователя, с причиной и NOT_RUN
  report; в Python/CLI используй `skip-verification`.
- Native verification не требует CLI-only Docker profile; используй доступные
  разрешённые инструменты в фактическом sandbox. Python Runner gates не меняются.
- Заблокированная или не выполненная проверка не считается успешной.
- При ограничениях среды сообщи причину; не обходи ограничения.

### 4. Reviewer и завершение

- Передай фактические изменения независимому Reviewer через Harness.
- Покажи пользователю замечания Reviewer и результаты Verification.
- Исправления выполняй через разрешённое продолжение Developer.
- После исправлений требуется повторное независимое ревью и актуальная
  проверка по правилам Harness.
- Запроси финальное одобрение конкретного результата.
- Только после него зафиксируй Done в состоянии выбранного backend Harness с актуальными changes/review/verification bindings.

Не объявляй задачу завершённой до финального одобрения пользователя.

## Сохранность проекта

- Сохраняй существующие изменения и untracked-файлы.
- Не откатывай изменения пользователя или других агентов автоматически.
- Не выполняй commit, push и разрушительные Git-операции без отдельного запроса.
- Одобрение плана или результата не разрешает commit или push.
- Не создавай фиктивные согласования, отчёты, идентификаторы сессий
  или успешные результаты проверок.

## Общение

Общайся на русском языке.
В каждом переходе указывай текущую стадию, результат и следующий шаг.

и какие действия это разрешает.

Для вопросов и объяснений без изменения проекта полный workflow не требуется.
Такой запрос не разрешает попутно менять исходники.
